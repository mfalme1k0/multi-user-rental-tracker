# Implementation Decisions and Trade-offs

This record accompanies the database, repository, and containerization work. Each decision states the reason for the chosen direction and the alternative considered.

| Decision | Choice | Reasoning and trade-off |
|---|---|---|
| Password storage | Store one Password4j bcrypt result in `users.password` as `TEXT NOT NULL`. | Password4j output is self-describing: it contains the algorithm, cost, salt, and digest. A separate salt column would duplicate information and make verification harder to evolve. The database stores only the hash; plaintext is never a repository concern. |
| Password hashing boundary | Keep hashing and verification in the Service/Auth layer; keep `SQLiteUserRepository` limited to persistence. | The repository should return the stored row and not know authentication policy. This keeps SQL integration simple and makes authentication testable with an injected hasher. The trade-off is that the service must always hash before calling `insert`. |
| Existing database migration | Use an explicit schema-version-3 legacy reset instead of retaining passwordless accounts. | `CREATE TABLE IF NOT EXISTS` cannot add `password` to an existing table. When the old users shape or an empty password from the intermediate migration is detected, the application drops `rentals`, `listed_items`, and `users`, then recreates the schema in one transaction. This is intentionally destructive because preserving usernames without valid credentials creates login and recovery ambiguity. Current-schema databases with real hashes are not reset. |
| Legacy passwordless rows | Do not retain them with an empty hash, default password, or generated credential. | An empty hash leaves a username that cannot log in and can conflict with registration. A generated or documented default password would be a security vulnerability. Dropping the legacy application tables gives the authentication layer a clean state. The trade-off is loss of legacy users and rental history, so the Docker upgrade procedure must back up or remove the old volume first. |
| Username uniqueness | Preserve case-insensitive uniqueness with `COLLATE NOCASE`. | Usernames that differ only by case should not become two identities. The migration also detects existing case-only duplicates and fails rather than silently merging accounts. |
| Self-rental trigger | Retain the existing `trg_rentals_no_self_rental` trigger. | The Service layer remains the readable authorization boundary, but the database trigger is a defense-in-depth invariant for direct SQL or future callers. It does not assume a single owner; it compares the renter with the selected item's owner. |
| Active-rental index | Retain the partial unique index on active rentals. | Multi-user operation still requires at most one active rental per item, while closed rental history remains unlimited. This is a cross-row integrity rule that belongs in SQLite as well as in service validation. |
| Transaction connection model | Keep per-operation connections and a `ThreadLocal` transaction connection. | The current application is a single-threaded CLI; users act sequentially, so the existing model preserves atomic multi-repository operations without a global connection. The trade-off is that it is not a complete concurrency model for a future server. That deployment change requires a redesign and review. |
| Ownership checks | Keep authorization checks in the Service layer, not in repository SQL. | The brief explicitly requires comparison of authenticated identity with `owner_id`. Putting this in repositories would mix persistence with session policy and make all callers inherit one workflow. Repositories still reject missing records and zero-row updates so services cannot mistake a no-op for success. |
| `findFirst()` removal timing | Remove the single-owner repository contract as part of the authentication/service integration slice, not while Transport still depends on owner startup flow. | The work plan correctly identifies `findFirst()` as invalid in the final multi-user design. Removing it before replacing the current `UserService` and Transport flow would leave the branch uncompilable and would force changes outside this ownership area. The contract removal is therefore a coordinated next step, with no new code allowed to depend on it. |
| Seed data strategy | Seed through an explicit, idempotent development path rather than baking mutable account data into the image. | A Docker image should remain reproducible and should not overwrite a user's persistent volume. Seed credentials must be generated with Password4j and documented as demo-only. The trade-off is one extra setup step for demonstrations. |
| Container persistence | Keep the named `/data` volume and `DB_PATH=/data/rental-tracker.db`. | The scaffold already matches the brief, so replacing it would add risk without value. The remaining work is empirical restart validation and documentation, not a new container architecture. |
| Browse pagination | Apply `LIMIT` and `OFFSET` in the repository, with stable `id ASC` ordering and one look-ahead row for `hasNext`. | The team decided to scale early. This bounds memory use and keeps filtering close to SQLite without requiring a separate count query. Transport remains responsible for navigation and rendering. |
| Atomic rental claim | Add `markRentedIfAvailable(itemId)` as a conditional update returning whether a row changed. | A read followed by an unconditional status update can race with another rental attempt. The conditional update lets the service claim availability inside its existing transaction and report a recoverable “already rented” business error when no row is changed. |
