# Multi-user Rental Tracker

A Java command-line application for a shared rental library. Multiple users can register, list items for rent, browse other users' listings, rent items, and track returns. Data is stored in SQLite and persists between application runs.

Built with Java 21+, Maven, SQLite, and a five-layer architecture enforced by ArchUnit. The project includes password hashing, authentication, ownership enforcement, centralized validation, structured logging, automated tests, CSV data import, and Docker support.

## Features

| Area | Capabilities |
|---|---|
| Authentication | Register, log in, and log out. Passwords are hashed before storage. |
| Items | List, view, delist, and relist your own items; view inventory with pagination. |
| Rentals | Browse other users' listings, rent available items, confirm returns, and view active rentals with pagination. |
| Multi-user support | Items are associated with their owners and rentals with authenticated renters. |
| Validation | User, Item, and Rental data are validated centrally before repository operations. |
| State machine | Enforces valid transitions between `AVAILABLE`, `RENTED`, and `UNLISTED`. |
| Persistence | SQLite with foreign keys, `CHECK` constraints, and a partial unique index for active rentals. |
| CSV import | Imports users, listed items, and rentals from CSV files, resolving external IDs to local database IDs. |
| Import reporting | Reports every imported record as `MATCHED`, `INSERTED`, or `REJECTED`, including rejection reasons. |
| Error handling | Displays readable errors, logs internal failures, and cleans up resources. |
| Logging | Structured events with timestamps, severity, event names, and contextual fields. |
| Containerization | Docker execution with persistent SQLite storage. |

## Running the application

Choose either local execution or Docker.

### Option 1: Run locally

From the project root:

**Run the application**

```bash
mvn compile exec:java
```

**Run tests**

```bash
mvn test
```

The configured JaCoCo report is available at `target/site/jacoco/index.html` when generated by the Maven lifecycle.

**Run the coverage gate**

```bash
mvn verify -Pcoverage-gate
```

The coverage gate currently requires 100% line and branch coverage. The project has not yet met both thresholds. See [Testing and coverage](#testing-and-coverage) for the last recorded results.

When running locally, the database defaults to `rental-tracker.db` in the working directory. The `DB_PATH` environment variable or the `rentaltracker.db` Java system property can override the location. The system property takes precedence.

### Option 2: Run with Docker

Docker builds and runs the application in a consistent environment without requiring Java or Maven on your computer. Because Rental Tracker is an interactive command-line application, use `docker compose run` for normal sessions; it connects your terminal directly to the Java process.

#### Recommended normal flow

From the project root, build the image and then start an interactive application session:

```bash
docker compose build
docker compose run --rm -it app
```

The first command builds the application image using the Dockerfile. Docker downloads missing base images and dependencies, and reuses cached build layers where possible. The second command starts the interactive Rental Tracker menu in the current terminal. Enter menu choices such as `1`, `2`, or `3`, then press **Enter**.

The `app` service is defined in `compose.yaml`. It uses `DB_PATH=/data/rental-tracker.db`, mounts the persistent database volume, and removes the temporary application container when the program exits. The named database volume is preserved.

#### One-command alternative

For a one-time build-and-run command, users can run:

```bash
docker compose run --build --rm -it app
```

This combines the image build and interactive run. It is useful for a first run or after source and build-configuration changes. For subsequent sessions without changes, use the two-step flow above and omit `--build`.

#### When should I rebuild?

| Situation | Command |
|---|---|
| First interactive run | `docker compose build` followed by `docker compose run --rm -it app` |
| Include source or build-configuration changes | `docker compose build` followed by `docker compose run --rm -it app` |
| Normal interactive run with no changes | `docker compose run --rm -it app` |
| One-time build and interactive run | `docker compose run --build --rm -it app` |

Docker reuses valid cached build layers where possible. Changes to `pom.xml` can invalidate the Maven dependency layer and require additional downloads. An interrupted build may also need to repeat an incomplete step.

#### Database persistence

The application stores its SQLite database at `/data/rental-tracker.db` inside the container. The Compose configuration mounts a named volume at `/data`.

- The database persists when the application exits and its temporary `docker compose run` container is removed.
- Each developer has a separate local database volume. Data is not automatically shared between computers.
- `docker compose down` removes Compose-managed containers and networks but preserves named volumes.

**Warning:** `docker compose down -v` deletes the Compose-managed named volume and its database data. Use it only when you intentionally want to reset the database.

#### View the application log file

While the application container is still running, open another terminal and find the container:

```bash
docker ps
```

Then use the displayed container name or ID to open a shell:

```bash
docker exec -it multi-user-rental-tracker-app-run-<id> sh
```

Inside the container, view the most recent log entries:

```bash
tail -n 100 /data/rental-tracker.log
```

To follow new log entries continuously:

```bash
tail -f /data/rental-tracker.log
```

You can also read the file directly without opening a shell:

```bash
docker exec multi-user-rental-tracker-app-run-<id> \
  tail -n 100 /data/rental-tracker.log
```

The exact container name may differ, so use the name or ID shown by `docker ps`.

#### Troubleshooting

Check the resolved Compose configuration:

```bash
docker compose config
```

If an older Compose container is still running and an interactive session is unavailable, stop it and start a new session:

```bash
docker compose down
docker compose run --rm -it app
```

If the application fails to start, inspect the error output before rebuilding or deleting Docker resources.

#### Docker image design

The Dockerfile uses a multi-stage build. Maven and the JDK compiler are used during the build stage, while the final image uses a Java runtime. Maven dependencies are downloaded in a separate build layer so Docker can reuse that layer when the POM remains unchanged.

## CSV data import

The application supports importing users, listed items, and rentals from a directory containing three CSV files.

The import merges exported data into an existing SQLite database. It resolves external IDs from the CSV files to the corresponding local database IDs, allowing imported rentals to reference the correct local items and users.

### Required files

The import directory must contain all three files:

```text
csv-export/
├── users.csv
├── listed_items.csv
└── rentals.csv
```

The required CSV headers are:

**`users.csv`**

```csv
id,username,password,created_at
```

**`listed_items.csv`**

```csv
id,owner_id,name,description,cost_per_day,status,created_at
```

**`rentals.csv`**

```csv
id,item_id,renter_id,start_time,end_time,returned_at,status
```

The `id` fields are external identifiers from the source database. They are used to resolve relationships during import rather than being assumed to be the destination database's primary keys.

### Build the executable JAR

From the project root:

```bash
mvn package
```

### Run an import

The CLI accepts the CSV directory as an argument:

```bash
java -jar target/rental-tracker-0.1.0-SNAPSHOT.jar import data/csv-export
```

The import uses the database configured for the application. You can override the database location using the `rentaltracker.db` Java system property.

**Recommended: use a working copy of the database for demonstrations.**

For example, if `data/rental-tracker.db` is your pristine demonstration database:

```bash
cp data/rental-tracker.db /tmp/rental-tracker-working.db

java -Drentaltracker.db=/tmp/rental-tracker-working.db \
  -jar target/rental-tracker-0.1.0-SNAPSHOT.jar \
  import data/csv-export
```

This allows you to inspect the imported data without modifying the original demonstration database.

### How the import works

The import processes the CSV files in dependency order:

1. **Users:** Existing users are matched by username. New users are inserted when no matching username exists.
2. **Listed items:** Each item's owner is resolved through the imported user mapping. Existing items are matched using their owner, name, daily cost, and description. Otherwise, valid new items are inserted.
3. **Rentals:** The item and renter references are resolved to local database IDs. Existing rentals are matched using their resolved item, renter, and start time. Otherwise, valid new rentals are inserted.

The importer maintains mappings between external identifiers and local database identifiers. This is important because an inserted user or item may receive a different primary key in the destination database.

### Validation and rejected records

Invalid records are rejected individually. A rejected record does not prevent subsequent valid records from being processed.

Examples of validation failures include:

- Blank required usernames.
- Unknown owner IDs.
- Blank required item names.
- Rentals referencing items or renters that cannot be resolved.
- Invalid values that violate the import validation rules.

Blank nullable item descriptions are normalized to SQL `NULL`.

Existing password hashes are carried across unchanged. The importer does not hash an already-hashed password again.

### Import report

The CLI prints aggregate totals and a result for every CSV data record.

Each record is reported as one of:

- `MATCHED` — A corresponding record already exists in the destination database.
- `INSERTED` — A new record was successfully inserted.
- `REJECTED` — The record could not be imported. Its rejection reason is displayed.

For example, the demonstration import produces:

```text
Import complete: inserted=4 matched=8 rejected=4
Record details:
  users.csv record 1: MATCHED
  users.csv record 2: MATCHED
  users.csv record 3: INSERTED
  users.csv record 4: REJECTED - username must not be blank
  listed_items.csv record 1: MATCHED
  listed_items.csv record 7: INSERTED
  listed_items.csv record 8: REJECTED - owner external id 9999 could not be resolved
  rentals.csv record 1: INSERTED
  rentals.csv record 2: REJECTED - item external id 9999 could not be resolved
```

The example is abbreviated; the actual CLI reports every record, including all matched, inserted, and rejected records.

Record numbers refer to CSV data-record positions, excluding the header. They are not necessarily physical file line numbers when CSV fields contain embedded newlines.

A successful import can contain rejected records. The aggregate summary makes those rejections visible rather than silently skipping invalid data.

### Repeat imports

The importer does not insert duplicate records when the same CSV data is imported again.

A repeat import reports existing records as `MATCHED` instead of inserting them again. Invalid records remain rejected and retain their rejection reasons.

The demonstration dataset has been tested with a first import and a repeat import. The first import produced:

```text
inserted=4 matched=8 rejected=4
```

The repeat import produced:

```text
inserted=0 matched=12 rejected=4
```

The working database checksum was identical before and after the repeat import, confirming that the second import made no database changes.

The import runs within a transaction. Record-level validation failures are reported individually; fatal import failures cause the transaction to roll back.

## Architecture

The application separates interactive input, business logic, persistence contracts, domain rules, and infrastructure.

- **Transport:** CLI menus, authentication flow, and paginated input/output.
- **Service:** Authentication coordination, validation, ownership enforcement, business rules, and transaction boundaries.
- **Repository:** Repository interfaces and SQLite persistence implementations.
- **Domain:** Entities, records, enums, and state-transition rules.
- **Infrastructure:** Database connections, schema initialization, and configuration.

ArchUnit tests enforce permitted dependency directions and prevent SQL access outside the appropriate persistence layer. Domain types are shared across layers rather than acting as a separate infrastructure dependency.

The service layer enforces business rules independently of the CLI, so changing menu options cannot bypass ownership or rental restrictions.

Password hashing and structured logging are cross-cutting concerns. Passwords never appear in logs, whether plaintext or hashed.

Architectural decisions are documented in `docs/architecture.md`.

## Database design

The SQLite schema contains four main tables:

- `users` — Unique usernames and password hashes.
- `listed_items` — Items associated with their owners through `owner_id`.
- `rentals` — Rental records associating items with their renters.
- `application_logs` — Structured, non-sensitive operational events with timestamps, severity, event names, JSON context, and optional user IDs.

The schema is initialized automatically when the database is created. The application then applies `src/main/resources/data.sql`, an idempotent development/demo seed containing two bcrypt-hashed users and six listings; it does not overwrite existing records.

### Database-enforced rules

- `PRAGMA foreign_keys = ON` is set for every connection.
- `CHECK` constraints limit item and rental statuses to valid values.
- `rentals.end_time` is required to be later than `rentals.start_time`.
- Invalid daily rental costs are rejected.
- A partial unique index allows at most one active rental per item.
- Foreign keys use `ON DELETE RESTRICT`.
- Usernames are unique.
- Password hashes are stored, never plaintext passwords.

Service-layer rules additionally prevent users from renting their own items or modifying items and returns they do not own.

See [`docs/database-design.md`](docs/database-design.md) for the detailed schema and constraint rationale.

## Authentication and user flow

On startup, users choose whether to log in or register.

```text
=== Rental Tracker ===
1. Log in
2. Register
>
```

Registration validates input, hashes the password, and stores the account. Duplicate usernames and invalid input produce readable errors.

Login verifies the supplied credentials. Invalid credentials produce an error without crashing the application or revealing internal details.

After successful authentication, the application identifies the current user and presents the main menu:

```text
=== Rental Tracker ===
1. List an item
2. View my inventory
3. Browse listings
4. Confirm a return
5. Exit
>
```

Users list items under their own accounts, browse other users' available listings, and rent items as themselves. The service layer, not merely the menu, enforces ownership and rental restrictions.

Exiting logs out the current user and closes the application.

## Item state machine

Supported transitions are:

- `AVAILABLE ↔ RENTED`
- `AVAILABLE ↔ UNLISTED`
- `RENTED → UNLISTED`

An item delisted while rented remains unlisted after the rental is returned. Relisting is prohibited while a rental is active.

Service rules and database constraints work together to preserve valid states and rental relationships.

## Validation and error handling

User, Item, and Rental data are validated centrally at the service boundary before repository operations.

Invalid input is rejected, including:

- Blank required fields.
- Negative rental costs.
- Rental durations below one day.
- Missing items.
- Attempts to rent one's own items.
- Attempts to modify another user's item or confirm a return without ownership.

Errors are shown as concise, user-friendly messages instead of database error codes or stack traces. Internal diagnostic details are recorded in structured logs without exposing sensitive information.

Recoverable errors return control to the menu. Unrecoverable startup failures are logged before the application exits. Database connections and other resources are cleaned up even when operations fail.

## Structured logging

Events are logged with a timestamp, severity level, event name, and relevant context fields.

Example format:

```text
2026-03-15T02:14:08Z | INFO  | rental.created    | rental_id=42 item_id=7 renter_id=3
2026-03-15T02:14:33Z | WARN  | validation.failed | entity=Item field=cost reason=negative
2026-03-15T02:14:38Z | ERROR | db.query          | op=rental.create error=constraint_violation
```

Significant rental events, validation failures, exceptions, and relevant database lifecycle events are logged. Plaintext passwords, password hashes, and other sensitive authentication details are never logged.

## Testing and coverage

Tests cover CRUD operations, state transitions, authentication, validation, ownership enforcement, logging, failure handling, and resource cleanup.

Integration tests use real SQLite databases with isolated, known state, and verify the resulting database state rather than relying solely on service return values.

Run the test suite:

```bash
mvn test
```

Inspect the JaCoCo report at `target/site/jacoco/index.html`.

Run the configured coverage gate:

```bash
mvn verify -Pcoverage-gate
```

Line and instruction coverage are 100%. Branch coverage is 99.71% (346/347). The single missed branch is a compiler-generated path in `DatabaseManager.usersTableHasPassword` for try-with-resources when `ResultSet.close()` fails. All observable behaviours of the method (password column present/absent, empty pragma result, query failure, and close failures including suppressed close-on-error) are covered by unit tests. The coverage gate does not fail on synthetic `AutoCloseable` close edges, since they are not application logic.
