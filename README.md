# Multi-user Rental Tracker

A Java command-line application for a shared rental library. Multiple users can register, list items for rent, browse other users' listings, rent items, and track returns. Data is stored in SQLite and persists between application runs.

Built with Java 21+, Maven, SQLite, and a five-layer architecture enforced by ArchUnit. The project includes password hashing, authentication, ownership enforcement, centralized validation, structured logging, automated tests, and Docker support.

## Features

| Area | Capabilities |
|---|---|
| Authentication | Register, log in, and log out. Passwords are hashed before storage. |
| Items | List, view, delist, and relist your own items; view inventory with pagination. |
| Rentals | Browse other users' listings, rent available items, confirm returns, and view active rentals with pagination. |
| Multi-user support | Associate items with their owners and rentals with authenticated renters. |
| Validation | Centrally validate User, Item, and Rental data before repository operations. |
| State machine | Enforce valid transitions between `AVAILABLE`, `RENTED`, and `UNLISTED`. |
| Persistence | SQLite with foreign keys, `CHECK` constraints, and a partial unique index for active rentals. |
| Error handling | Display readable errors, log internal failures, and clean up resources. |
| Logging | Structured events with timestamps, severity, event names, and contextual fields. |
| Containerization | Docker execution with persistent SQLite storage. |

## Running the application

Choose either local execution or Docker.

### Option 1: Run locally

From the project root:

**Run the application**

```bash
mvn compile exec:java
```

**Run tests**

```bash
mvn test
```

The configured JaCoCo report is available at `target/site/jacoco/index.html` when generated by the Maven lifecycle.

**Run the coverage gate**

```bash
mvn verify -Pcoverage-gate
```

The coverage gate checks the configured line and branch coverage requirements.

When running locally, the database defaults to `rental-tracker.db` in the working directory. The `DB_PATH` environment variable or the `rentaltracker.db` Java system property can override the location. The system property takes precedence.

### Option 2: Run with Docker

Docker builds and runs the application in a consistent environment without requiring Java or Maven on your computer.

#### Rebuild and start with Docker Compose

From the project root, run:

```bash
docker compose up --build
```

Use this command when the image has not been built yet or when you need to rebuild it to include application or build-configuration changes.

Docker downloads missing base images and dependencies, builds the application, and starts the interactive CLI. The first build may take several minutes.

#### Normal runs

After a successful build, run:

```bash
docker compose up
```

**Use this command for everyday use when the image already exists.** It does not explicitly request a rebuild, avoiding unnecessary build work and repeated dependency downloads.

If the required image is missing locally, Docker Compose may need to build or obtain it, depending on the configuration and available images.

#### When should I rebuild?

| Situation | Command |
|---|---|
| First run | `docker compose up --build` |
| Include source or build-configuration changes | `docker compose up --build` |

Docker reuses valid cached build layers where possible. Changes to `pom.xml` can invalidate the Maven dependency layer and require additional downloads. An interrupted build may also need to repeat an incomplete step.

#### Database persistence

The application stores its SQLite database at `/data/rental-tracker.db` inside the container. The Compose configuration mounts a named volume at `/data`.

- The database persists when the application exits and its temporary container is removed.
- Each developer has a separate local database volume. Data is not automatically shared between computers.
- `docker compose down` removes Compose-managed containers and networks but preserves named volumes.

**Warning:** `docker compose down -v` deletes the Compose-managed named volume and its database data. Use it only when you intentionally want to reset the database.

#### Troubleshooting

Check the resolved Compose configuration:

```bash
docker compose config
```

View recent service logs:

```bash
docker compose logs --tail=50 app
```

If the application fails to start, inspect the error output before rebuilding or deleting Docker resources.

#### Docker image design

The Dockerfile uses a multi-stage build. Maven and the JDK compiler are used during the build stage, while the final image uses a Java runtime. Maven dependencies are downloaded in a separate build layer so Docker can reuse that layer when the POM remains unchanged.

## Architecture

The application separates interactive input, business logic, persistence contracts, domain rules, and infrastructure.

- **Transport:** CLI menus, authentication flow, and paginated input/output.
- **Service:** Authentication coordination, validation, ownership enforcement, business rules, and transaction boundaries.
- **Repository:** Repository interfaces and SQLite persistence implementations.
- **Domain:** Entities, records, enums, and state-transition rules.
- **Infrastructure:** Database connections, schema initialization, and configuration.

ArchUnit tests enforce permitted dependency directions and prevent SQL access outside the appropriate persistence layer. Domain types are shared across layers rather than acting as a separate infrastructure dependency.

The service layer enforces business rules independently of the CLI, so changing menu options must not bypass ownership or rental restrictions.

Password hashing and structured logging are cross-cutting concerns. Passwords must never appear in logs, whether plaintext or hashed.

Document architectural decisions in `docs/architecture.md` and update them when the implementation changes.

## Database design

The SQLite schema contains four main tables:

- `users` — Unique usernames and password hashes.
- `listed_items` — Items associated with their owners through `owner_id`.
- `rentals` — Rental records associating items with their renters.
- `application_logs` — Structured, non-sensitive operational events with timestamps, severity, event names, JSON context, and optional user IDs.

The schema is initialized automatically when the database is created.

### Database-enforced rules

- Enable `PRAGMA foreign_keys = ON` for every connection.
- Use `CHECK` constraints for valid item and rental statuses.
- Require `rentals.end_time > rentals.start_time`.
- Reject invalid daily rental costs.
- Use a partial unique index to allow at most one active rental per item.
- Use foreign keys with `ON DELETE RESTRICT`.
- Enforce unique usernames.
- Store password hashes, never plaintext passwords.

Service-layer rules additionally prevent users from renting their own items or modifying items and returns they do not own.

See [`docs/database-design.md`](docs/database-design.md) for the detailed schema and constraint rationale.

## Authentication and user flow

On startup, users choose whether to log in or register.

```text
=== Rental Tracker ===
1. Log in
2. Register
>
```

Registration validates input, hashes the password, and stores the account. Duplicate usernames and invalid input produce readable errors.

Login verifies the supplied credentials. Invalid credentials must not crash the application or reveal internal details.

After successful authentication, the application identifies the current user and presents the main menu:

```text
=== Rental Tracker ===
1. List an item
2. View my inventory
3. Browse listings
4. Confirm a return
5. Exit
>
```

Users list items under their own accounts, browse other users' available listings, and rent items as themselves. The service layer—not merely the menu—enforces ownership and rental restrictions.

Exiting logs out the current user and closes the application.

## Item state machine

Supported transitions are:

- `AVAILABLE ↔ RENTED`
- `AVAILABLE ↔ UNLISTED`
- `RENTED → UNLISTED`

An item delisted while rented remains unlisted after the rental is returned. Relisting is prohibited while a rental is active.

Service rules and database constraints work together to preserve valid states and rental relationships.

## Validation and error handling

Validate User, Item, and Rental data centrally at the service boundary before repository operations.

Reject invalid input, including:

- Blank required fields.
- Negative rental costs.
- Rental durations below one day.
- Missing items.
- Attempts to rent one's own item.
- Attempts to modify another user's item or confirm a return without ownership.

Display concise, user-friendly error messages instead of database error codes or stack traces. Record internal diagnostic details in structured logs without exposing sensitive information.

Recoverable errors should return control to the menu. Unrecoverable startup failures should be logged before the application exits. Database connections and other resources must be cleaned up even when operations fail.

## Structured logging

Log events with a timestamp, severity level, event name, and relevant context fields.

Example format:

```text
2026-03-15T02:14:08Z | INFO  | rental.created    | rental_id=42 item_id=7 renter_id=3
2026-03-15T02:14:33Z | WARN  | validation.failed | entity=Item field=cost reason=negative
2026-03-15T02:14:38Z | ERROR | db.query          | op=rental.create error=constraint_violation
```

These examples illustrate the intended format; actual output depends on the logging implementation.

Log significant rental events, validation failures, exceptions, and relevant database lifecycle events. Never log plaintext passwords, password hashes, or other sensitive authentication details.

## Testing and coverage

Tests should cover CRUD operations, state transitions, authentication, validation, ownership enforcement, logging, failure handling, and resource cleanup.

Use real SQLite databases with isolated, known state for integration tests. Verify resulting database state rather than relying solely on service return values.

Every new service-layer method should have tests, and existing behavioral checks must remain intact.

Run the test suite:

```bash
mvn test
```

Inspect the JaCoCo report at `target/site/jacoco/index.html`.

Run the configured coverage gate:

```bash
mvn verify -Pcoverage-gate
```

The project targets 100% line and branch coverage. Investigate uncovered code and document any justified gaps.
